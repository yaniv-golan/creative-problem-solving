# Does the pipeline beat a plain prompt? — pre-registered design

**Status: partially run 2026-08-17 — one of the two pre-registered prompts is complete.**

> Skill vs baseline on distinct mechanisms: **6.60 vs 4.00** (retention) — a delta of +2.60
> against a pre-registered threshold of 1.0. The blinded judge's own two-group split recovered
> the arms **10/10**.
>
> The second prompt — the strategic `operating-model-deep` question — **ran on 2026-08-18 and
> returned +0.60, below the 1.0 threshold.** Since the decision rule below requires an effect on
> **both** prompts, what stands is a partial result on one: the exact situation the two-prompt
> design was chosen to prevent.
>
> Full write-up: [`results/vs-plain-prompt.md`](results/vs-plain-prompt.md).

Design, metric and decision rule were fixed before any data was seen, for the same reason
`EXPERIMENT-separation.md` is: this project has read a preferred conclusion out of a small
sample four times in one iteration, and pre-registration is the only thing that reliably stops
it.

## The question

On a **strategic** problem, does the shipped pipeline produce a better option set than
the same model answering the same prompt with no skill at all?

## Why this is now the load-bearing experiment

Everything else has been measured. This has not, and the skill's entire remaining claim rests
on it:

- **Iteration 1's apparent sweep was an artifact** — its discriminating assertions tested
  process compliance, which a baseline cannot pass by construction.
- **Iteration 2, the one clean skill-vs-baseline comparison, the baseline WON** 17/18 to 14/18.
  It tested two bounded questions and a negative trigger — no strategic problem.
- **Iterations 3–5 reused stale baselines** from iteration 2 rather than re-running them.
- **The separation pilot** compared dispatched vs narrated — *both arms had the full pipeline.*
  Neither was tested against a plain prompt.

So: the skill has never been cleanly measured against the thing it has to beat, on the class of
problem where it claims to win.

## Design

- **Arms.** A: the released skill, deep mode. B: identical prompt, skill removed, via
  `cowork-harness skill … --ablate-skill` — the harness's built-in negative control, so the
  baseline is generated by the same runtime, same model, same tier, not by a stale transcript.
- **Model** pinned `claude-opus-5`. **Commit frozen** at the release tree.
- **Prompts — two, in different domains.** Every deep-mode measurement in this project's
  history had used a single strategic prompt; one prompt cannot separate "the pipeline works"
  from "the pipeline works on this question."
  1. `operating-model` — a strategic question about an operating model under AI pressure.
     **Run 2026-08-18: +0.60, did not clear.** That dataset spans four skill hashes; a clean
     single-build re-measurement scored the same comparison at +0.00 and +1.00 under two blind
     judges, so the metric is judge-dominated.
  2. `holdout-retention` — "losing senior engineers at 18 months, comp is competitive, it's not
     the money" (eval 5's held-out problem, a different domain, already validated as
     deep-qualifying — and the one where a plain answer beat the skill in iteration 5 by
     refusing the user's premise)
- **5 runs per arm per prompt** → 20 runs when both are complete; 10 run so far.

## Metric

The instrument validated by the separation pilot: **blinded mechanism-level distinctness**.
It earned trust there by independently discovering a latent grouping (model) nobody told it
about.

Primary: `n_distinct_mechanisms` — options differing in **kind** (how money is made, how a
claim is held, what changes about the job) rather than **degree** (size, stage, sector, hold
period). Secondary: tail boldness; whether causal mechanisms are stated; mechanisms unique to
one answer; and — new for this experiment, because it is where iteration 5 says the baseline
won — **whether the answer tests a premise the user ruled out.**

Explicitly *not* `scripts/diversity.py`: its kernel is lexical, and this repo documents it
scoring pools 94–99% distinct while the same mechanism recurred in most passes.

## Controls

- Process vocabulary scrubbed from all answers before judging.
- Judge told to ignore length, formatting, and chat-vs-memo shape — the format asymmetry that
  confounded the separation pilot.
- Deterministic shuffle; the judge sees unlabelled answers with no arm key.
- Canonical mechanism labels reused across answers so cross-answer clustering works.
- Both arms judged together, per prompt, so the comparison is within-question.

## Decision rule (fixed in advance)

Per prompt, compare arm means on `n_distinct_mechanisms`.

- **Skill − baseline ≥ 1.0 mechanism on both prompts** → the pipeline earns its cost. The
  README may claim it.
- **|difference| < 1.0 on both** → **no detected effect.** The honest README says the skill
  produces a comparable option set with better discipline (verification, honesty rule, length
  control) and does **not** claim more diversity.
- **Split** → report both, claim nothing, and say which prompt it won on.

A result where the baseline wins is a publishable outcome, not a failure to hide. Iteration 2
is this repo's most credible artifact precisely because it recorded one.

## What this cannot settle

Whether the four phases ran. Since dispatch was removed before release, generation is in-context by design
and has no tool-stream signature. This experiment measures the **output**, which is what the
user gets; it cannot attribute a difference to any particular phase.

## Results

[`results/vs-plain-prompt.md`](results/vs-plain-prompt.md) — **effect detected on the prompt
that has been run**, by a margin of 2.6× the detection threshold. The rule fixed above requires
both prompts, so the README states the single result and its scope rather than claiming the
rule was met.

One process note worth keeping: the first attempt produced 10 baseline runs and 0 treatment
runs, because `--ablate-skill` composed with `--repeat` runs only the ablated arm — and
reported `PASS — 5/5`. Every run in the final dataset was individually verified from
`result.json` (`ablated`, `context.availableSkills`, `skillActivity`) before analysis.
